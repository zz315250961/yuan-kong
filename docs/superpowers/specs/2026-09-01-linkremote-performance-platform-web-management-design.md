# LinkRemote 性能、平台与 Web 管理端设计

状态：用户已确认
日期：2026-09-01

## 1. 背景与目标

LinkRemote 当前基于 RustDesk 客户端，已经有 Windows、Android 远控能力和自建的账号 API，但视频链路中的 60 FPS 定制没有贯穿采集、QoS、编码器时基与码率模型；Android 画质选择也没有可靠地控制被控端采集分辨率。仓库还保留上游多平台发布任务，而现有 Flutter Web 是未完成的远控预览客户端，不适合作为账号管理页继续扩建。

本项目分为三个可独立验收、可独立回滚的子项目：

1. 修复视频链路的帧率、码率和 Android 采集画质一致性，并补齐可观测指标。
2. 将正式发布范围收敛为 Windows x64、Android arm64 和 Web 账号管理端。
3. 基于现有账号 API 建立同源、响应式的 Web 账号与设备管理页。

“保证帧率和画质”在这里定义为：在设备编码能力和网络带宽允许时充分利用 60 FPS；拥塞或性能不足时有确定、可观测、带滞回的降级顺序，避免固定 60 FPS 造成每帧码率骤降。它不是对任意设备和任意网络承诺恒定 60 FPS。

## 2. 已确认范围

### 正式支持与发布

- Windows x64 桌面客户端。
- Android arm64-v8a，覆盖当前主流 64 位安卓真机。
- Web：仅个人账号和个人设备管理，不提供浏览器远程控制。

### 不在本期范围

- macOS、Linux、iOS、Android armv7/x86/x86_64 模拟器的正式构建和发布。
- 浏览器远控、文件传输、远程终端或摄像头查看。
- 管理员后台、用户封禁、审计报表或多租户组织管理。
- 本轮直接部署到生产服务器；交付代码、测试、构建产物和部署说明，部署需单独授权。
- 删除上游其他平台源码。它们只从发布入口和自动 CI 中退出，以降低以后同步 RustDesk 上游的冲突成本。

## 3. 方案选择

### 方案 A：独立的轻量 Web 管理页，由现有 Python API 同源提供（采用）

在 `server/linkremote-api/web/` 维护无构建依赖的 HTML、CSS 和模块化 JavaScript，`app.py` 提供静态文件和 Web 会话接口。原生客户端继续使用 Bearer Token；Web 使用 Secure、HttpOnly、SameSite Cookie。优点是复用现有 API、部署单一、下载体积小、不会依赖残缺的 Flutter/Rust Web bridge。代价是 Web UI 需要单独维护少量前端代码。

### 方案 B：从 Flutter 客户端抽取 Web 管理壳（不采用）

可以复用部分 Dart 模型和视觉组件，但当前 `flutter/web` 平台工程缺失，Web bridge 含大量未实现接口，主入口也强耦合远控状态。为了一个管理页修复整套 FFI 和依赖树，成本和回归风险明显偏高。

### 方案 C：新增 React/Vue 管理项目（不采用）

组件生态成熟，但会引入 Node 工具链、依赖更新和第二套构建发布流程。当前功能只有认证、账户资料和设备列表，不足以证明这项复杂度有价值。

## 4. 视频链路设计

### 4.1 先修正确性，再调参数

第一阶段不追求凭经验继续增大帧率，而是建立以下可测试的不变量：

- 客户端允许的 FPS 范围与服务端 QoS 范围一致；本产品默认 60，最低 10，正式 UI 最大 60。
- 用户设置的最大 FPS 永远是上限，包括 Android，不得被平台分支重新抬高。
- QoS 延迟区间互斥且全部可达；网络变差快速降级，连续三个良好样本后才允许升级。
- 硬件编码器初始化帧率与产品最大目标一致，不再固定为 30。
- 码率预算随目标 FPS 调整，但采用次线性系数和上限，避免从 30 到 60 时简单翻倍压垮链路。
- Android 采集缩放由当前连接实际选择的画质驱动，不读取被控端无关的全局默认值。

建议的初始 QoS 区间为：

- `<100 ms`：良好，动态画面可逐步增加码率/FPS。
- `100–250 ms`：可用，保持当前状态，禁止激进增码率。
- `250–500 ms`：拥塞，先降低码率比例，再按用户 FPS 上限降低发送帧率。
- `>=500 ms` 或响应等待超过 2 秒：严重拥塞，快速降到安全帧率，恢复时应用滞回。

具体数值封装为纯函数并由表格测试覆盖边界值 `99/100/249/250/499/500`，避免再次出现提前匹配导致分支不可达。

### 4.2 帧率与码率

编码配置新增显式目标 FPS，HWRAM 和 VRAM 都从同一个配置值初始化。动态 QoS 仍通过抓帧间隔控制实际发送帧率；编码器 FPS 表示其速率控制的时间基和能力上限。

码率使用以下模型：

`目标码率 = 分辨率基准码率 × 画质比例 × FPS 系数`

FPS 系数以 30 FPS 为基准，使用 `sqrt(target_fps / 30)`，并限制在 `0.75–1.45`。因此 60 FPS 的预算约为 30 FPS 的 1.41 倍，而不是保持不变或直接翻倍。现有硬件编码器的最小/最大码率限制继续作为最终边界。

### 4.3 Android 采集画质

`VideoQoS` 保存每个连接最近一次有效的画质选择，并暴露当前生效的采集策略：

- Best：全分辨率采集。
- Balanced、Low：允许半分辨率采集，以保护主流安卓设备的编码帧率。
- 多控制端同时连接时采用最新有效的用户选择，与现有码率策略一致。

当策略在全分辨率和半分辨率之间切换时，设置视频服务的刷新标志，让采集器和编码器安全重建；不在编码线程中修改全局用户默认配置。切换过程失败时保留旧策略并记录原因，不进入反复重启循环。

现有关闭的 Android MediaCodec 直通实验路径本期不重新启用。先保留源码但用明确的实验特性边界隔离，避免它参与正式构建逻辑；只有独立兼容性测试通过后再评估删除或恢复。

### 4.4 可观测性与验收

现有质量监视器补充：

- 用户目标 FPS、QoS 目标 FPS、实际采集/编码/解码/渲染 FPS。
- 当前分辨率、半分辨率状态、编码器、目标/实际码率。
- RTT、平滑延迟、当前 QoS 区间、直接连接或中继。
- 编码失败数、解码丢帧数和接收队列深度（能从现有数据取得的先接入，缺少数据的指标不伪造）。

性能验收采用一台 Windows x64 和一台 Android arm64 真机，在同一局域网与限速/加延迟网络各运行固定脚本场景。先记录当前版本基线，再要求新版本：

- 无静止画面和快速滚动场景的崩溃、黑屏或无限重连。
- Best 在 Android 上确实切换为全分辨率，Balanced/Low 按策略切换为半分辨率。
- 60 FPS 设置时硬件编码器报告的 FPS 上限不再是 30。
- 受限网络下 QoS 能进入每个区间，恢复时不会在阈值附近每秒来回切换。
- 同场景实际 FPS 不低于基线 95%，并在相近 FPS 下提高动态画面的每帧码率预算。视觉质量最终由真机录屏并排确认，不能用目标码率代替主观画质结论。

## 5. Web 管理端设计

### 5.1 页面与功能

响应式单页管理端包含：

- 登录。
- 邮箱注册与验证码发送。
- 忘记密码与验证码重置。
- 当前账号信息、修改绑定邮箱、退出登录。
- 设备列表：设备名、远控 ID、系统、最近登录时间。
- 刷新列表、复制远控 ID、从账号列表删除设备。

设备 API 当前把状态固定为在线，因此 Web 不展示虚假的在线/离线标识。删除的文案明确为“从账号列表移除”，不暗示它会封禁设备或阻止远控。

### 5.2 API 与会话

现有原生客户端契约保持不变：`/api/login` 等接口继续返回 Bearer Token。为 Web 增加同源会话模式：

- Web 登录成功后设置 `HttpOnly; Secure; SameSite=Lax; Path=/` Cookie。
- `_auth_user` 同时接受 Bearer Token 和 Web Cookie，Bearer 优先。
- Web 登出删除服务端 token 并清除 Cookie。
- 所有改变状态的 Cookie 请求校验 `Origin`/`Host` 同源；Bearer 客户端不受此校验影响。
- 生产环境只通过 HTTPS 暴露管理页和 API，不把 token 放入 URL、日志或 `localStorage`。
- CORS 从任意来源 `*` 收敛为配置的管理站点来源；未配置时仅允许同源。预检声明补全 `DELETE`。

设备列表响应补充真实的 `last_login` 字段，但保持原有字段兼容客户端。所有错误采用现有 `{"error":"..."}` 结构，前端对 401 统一回到登录页，对网络错误提供重试，不清空用户填写中的非密码字段。

### 5.3 静态资源与部署

`app.py` 仅按白名单提供 `/`、`/assets/app.css`、`/assets/app.js` 和图标，未知路径返回 404；不开放任意文件系统路径。浏览器缓存 HTML 为 `no-cache`，带内容版本的 CSS/JS 可长缓存。

交付反向代理示例：同一 HTTPS 域名把 `/api/` 和静态管理页转发到 21114。远控所需的 hbbs/hbbr 端口保持现状；因为 Web 不做远控，不开放 21118/21119。

## 6. 平台与发布设计

- `remote-desk-build.yml` 是唯一正式发布工作流。
- Windows 只构建 x86_64，并保留 `--hwcodec --vram`。
- Android 只构建 arm64-v8a，并保留 `flutter,hwcodec`。
- Web 管理端不执行 Flutter Web 构建；CI 运行 Python API 测试和静态资源契约测试，并打包服务器管理端文件。
- 上游 `flutter-tag.yml`、`flutter-nightly.yml`、`fdroid.yml` 不再响应本仓库的标签或定时事件，仅保留手动触发，方便将来同步上游时比较。
- `flutter-ci.yml` 缩小为 Windows/Android 相关检查或仅手动触发，避免每次提交验证已退出正式支持的平台。
- Docker 镜像从 `latest` 改为经过实际服务器验证的明确版本或 digest；在没有取得生产服务器当前镜像摘要前，不猜测版本、不修改部署镜像。

## 7. 测试策略

所有行为修改执行测试先行：先增加会失败的回归测试，再写最小实现。

- Rust 单元测试：QoS 区间边界、FPS 上限、滞回、FPS 码率系数、Android 画质到采集策略映射。
- Python `unittest`：认证、Cookie/Bearer 双会话、同源校验、CORS、设备列表 `last_login`、删除权限隔离、静态文件白名单。
- Web 测试：浏览器级登录、列表、删除、401 跳转和窄屏布局；如果本机无浏览器自动化依赖，至少以 HTTP 契约测试和静态 lint 为门槛，并在发布前执行人工浏览器验收。
- 工作流测试：YAML 解析、触发器检查、产物名称和架构矩阵断言。
- 构建验证：Windows x64 和 Android arm64 正式命令；本机缺少 Flutter/Android 工具链时，明确记录未执行项，由 GitHub Actions 补齐，不把静态检查冒充构建成功。

## 8. 实施顺序与回滚

1. 视频 QoS 与 Android 画质正确性，先单元测试，再实现。
2. 编码器 FPS 和码率模型，分别验证软件、HWRAM、VRAM 编译路径。
3. 质量监视器指标与真机基线记录。
4. Web API 安全和契约测试。
5. Web 管理页面及响应式验收。
6. 发布矩阵收敛和服务器打包说明。

每一阶段单独提交，不改动无关模块。若视频改动出现回归，可以只回滚视频提交，Web 和发布精简不受影响；若 Web 会话模式出现问题，原生 Bearer Token 路径仍然可用。

## 9. 安全与数据约束

- 不把邮箱密码、验证码、Bearer Token、Cookie 或 SMTP 密码写入仓库、测试快照、日志和知识库。
- 测试使用临时 SQLite 数据库和虚构邮箱。
- 设备删除严格按当前认证用户的 `user_id + uuid` 过滤。
- 静态文件路径使用固定映射或解析后目录边界检查，防止目录穿越。
- 生产部署前必须配置 HTTPS、可信代理来源和备份；本设计不授权自动上传或部署。

固定场景、记录字段和发布门槛见 `docs/performance-validation.md`。
